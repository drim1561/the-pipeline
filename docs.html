How the-pipeline works.

The inner workings of the copilot: the moving parts, the loop that runs around every session, and where the system keeps its memory. Everything here warns; only one thing decides, and he is not software.

documentation · updated july 2026

The moving parts

Three tiers, deliberately different jobs

The design rule the whole system follows: push work down this table. If a check is mechanical, it belongs in a script, not in a prompt.

PartWhat it isCost when idle
skills Procedural workflows that load only when invoked zero until the command is typed
subagents Fresh-context specialists dispatched for one bounded job, mostly read-only one spawn each, on the smallest model that does the job
scripts + hooks Plain Python that needs no model at all zero tokens, ever
Skills

Seven commands, one per moment of the search

Each is a slash command that loads its workflow only when called. The orange stop is the one that only records what a human already did.

  • /new-applicationScaffold

    Turns a job posting into a tailored application: verify the posting, screen the fit, draft against the locked fact file, run the independent QA gate. Ends staged, never sent.

  • /submit-applicationRecord

    Runs after the human presses submit, never before. One guarded script writes the tracker, an exact snapshot of what was sent is preserved, a follow-up lands on the calendar, and the channel it came through is recorded.

  • /triage-inboxReconcile

    Sweeps the inbox, classifies recruiter and ATS replies, and reconciles them against the tracker. Suggested responses are staged as drafts.

  • /prep-interviewPrepare

    Builds a study card from a curated story library, the job description, and every prior round's debrief, so no story gets told twice to the same company.

  • /log-interviewDebrief

    Post-interview capture: what was asked, how it went, stage advanced in the tracker, thank-you note staged for review.

  • /review-interviewCoach

    The coaching layer. Grades a call transcript against a storytelling playbook and tracks recurring themes across interviews, honestly.

  • /drill-storyRehearse

    Practice loop: tell a story out loud, paste the voice-to-text, get graded on arc, hedging, and whether the closing line landed.

Specialists

Four subagents, one bounded job each

Each runs in a fresh context with only what it needs, and none of them can write to memory or the tracker.

  • job-fit-screener Scores a posting against the real stack and targets, Tier 1 to 4, before any tailoring time is spent. A fast no is a feature.
  • application-reviewer The independent QA gate: every figure checked against the fact file, invented claims failed, voice checked against the profile.
  • company-research A read-only research brief on the company and role before an interview or a letter that warrants one.
  • tracker-auditor Hygiene: duplicates, stale stages, and mismatches between the tracker and the application folders on disk.
No model required

The deterministic layer

Anything mechanical runs as plain Python. Zero tokens, same result every time, and the only code allowed to touch the important files.

ScriptJob
update_pipeline.py The only writer the tracker has. Atomic saves, a stage-downgrade guard, terminal rows cannot silently reopen, and every submission records how it started.
add_lead.py The leads inventory writer: atomic, deduplicates on posting URL.
render_resume.py Deterministic resume tailoring inside the document itself, plus a warn-only style lint against the resume rulebook.
audit_consistency.py Drift check across instructions, cheatsheet, and config after any toolkit change. Memory that goes stale is worse than no memory.
archive_closed_applications.py Moves closed application folders whole into the archive. Nothing is ever deleted.
export_public_toolkit.py Mirrors the engine to a public repo through an allowlist and a PII scan, so code can be shared without the data ever leaving.
The session loop

What runs around every conversation

Hooks fire at fixed moments of every working session. All of them warn; none of them block. This page you are reading is the last step of the loop.

  • SESSION STARTBriefed before work begins

    A hook reads the tracker and prints the day's pipeline state, follow-ups due, and the command cheatsheet straight into the session. No cold starts.

  • DURING WORKThree guards ride along

    A delete guard before any shell command (move, never delete), a style check after edits to letters, and a row-count verification after any tracker write.

  • SESSION STOPThe pages rebuild themselves

    Plain Python re-reads the tracker and rewrites the dashboard pages, then commits a local snapshot of the session's work. No model involved.

  • DEPLOYPrivate and public ship together

    The full private dashboard deploys behind a login; this public site gets the shared view with contact names scrubbed on the way out.

  • SELF-CHECKFailures don't stay silent

    Deploy outcomes land in a status file that the next session's briefing reads first. The system notices its own failures across sessions.

Memory

Where the system remembers

Four layers, from most curated to most disposable. Only the index of the middle layer loads by default; everything else loads on demand.

  • Curated core, versioned in git. Standing instructions, one canonical fact file that every figure traces to, a voice profile, eleven sourced stories.
  • Auto-memory, one fact per file. Durable preferences and corrections with a one-line index. Only the index loads each session; bodies load when relevant.
  • Session layer, disposable by design. Transcripts and working buffers, auto-pruned on a schedule.
  • The staleness audit. A deterministic drift check keeps the layers agreeing with each other, because one fact should live in one place.
  • The asymmetry that matters. Subagents never see memory. Canonical facts are passed to them explicitly, so a correction must land in their definition files, not just in conversation.
The invariants

Rules wired in, not hoped for

These hold everywhere in the system, and each one exists because of a real lesson, not a hypothetical.

  • One writer touches the tracker. A single script with atomic writes, a downgrade guard, a terminal-reopen guard, and row-count verification after every write.
  • Nothing sends without a human. Applications, replies, thank-you notes: everything stops as a staged draft. There is no code path that submits anything.
  • Move, never delete. Closed work is archived whole with its full history, and a guard warns on any command that would destroy instead of move.
  • One source of truth per fact. Every number on the dashboard and in every document traces to a single canonical file. Figures cannot drift and claims cannot grow.
  • Hooks warn, humans decide. Every automated check is advisory. The system makes problems visible; it does not make choices.
